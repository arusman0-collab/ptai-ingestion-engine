# PT-AI INGESTION ENGINE

## Replit Master Build Specification / PRD v1.1

You are building the ingestion and archival subsystem for a larger project called **PT-AI**.

Read this entire specification before writing code.

Do not simplify or redesign the fundamental architecture without explaining why.

---

# 1. PROJECT PURPOSE

PT-AI is a non-commercial digital knowledge-preservation project initially focused on the documented sermons, lectures, writings, transcripts, books, and related source material of **Rev. Stephen Tong**.

The long-term objective is not merely to build a chatbot.

The durable asset is a:

**Digital Scholarly Archive + Provenance System + Retrieval Layer**

that AI models can reason over.

The reasoning LLM is replaceable.

The archive is not.

The architecture must eventually support additional Christian thinkers, theologians, preachers, historical figures, and sources referenced by Stephen Tong without requiring a fundamental redesign.

Possible future collections may include people such as Augustine, Calvin, Luther, Billy Graham, Nabeel Qureshi, and others.

Therefore:

DO NOT design this as a Stephen-Tong-specific chatbot.

Design it as a reusable scholarly ingestion and archival platform whose first collection is Stephen Tong.

---

# 2. CORE DESIGN PRINCIPLE

PT-AI must optimize for:

1. Preservation
2. Provenance
3. Source fidelity
4. Reproducibility
5. Auditability
6. Traceable citations
7. Offline/local operation
8. Portability
9. Replaceable AI models
10. Long-term archival integrity

The system must always distinguish:

ORIGINAL SOURCE

from

EXTRACTED / TRANSCRIBED MATERIAL

from

AI-DERIVED MATERIAL.

AI-generated material must never silently become a primary historical source.

# 4. REPLIT'S ROLE

Replit is the DEVELOPMENT environment.

It is NOT assumed to be the permanent archive host.

Build the application in Replit so that it can be:

1. developed in Replit,
2. tested using local/test services,
3. exported as normal source code,
4. packaged using Docker,
5. deployed onto the Oracle Linux PT-AI server,
6. pointed at persistent `/ptai-data`,
7. connected to local Ollama and Qdrant,
8. operated without Replit afterward.

Do not introduce proprietary Replit dependencies into the core ingestion engine.

Replit-specific conveniences are acceptable for development, but the core application must remain independently deployable.

# 10. WORK VS MANIFESTATION

This distinction is extremely important.

One intellectual work or sermon can have multiple manifestations.

Example:

Stephen Tong sermon
├── original video
├── audio
├── official transcript
├── Buletin PILLAR article
├── translated transcript
└── excerpt

Do not automatically treat each manifestation as a completely unrelated intellectual work.

The schema must allow:

CANONICAL WORK

and

MANIFESTATIONS.

Do not silently merge uncertain duplicates.

Flag them for human review.

# 39. CURRENT PT-AI ANSWERING PRINCIPLE

The existing PT-AI prototype already follows an important rule:

PT-AI answers questions using retrieved archive evidence rather than treating the LLM's pretrained knowledge as authoritative.

Maintain compatibility with this principle.

The reasoning layer should be able to receive retrieved evidence formatted approximately as:

[ST-000001 | chunk 4 | Filsafat Asia: Bagian 1]

<exact evidence text>

The reasoning layer can then cite Source IDs.

---

# 40. INSUFFICIENT EVIDENCE BEHAVIOR

PT-AI must support a strict archival answer mode.

When retrieved sources genuinely do not support an answer, the reasoning layer can respond:

"The current PT-AI archive does not contain sufficient evidence to answer this reliably."

The ingestion engine itself should therefore prioritize retrieval quality and provenance over simply returning something.

# 58. ERROR PHILOSOPHY

Never hide uncertainty.

It is preferable for PT-AI to say:

NEEDS REVIEW

than silently create a false historical record.

It is preferable to retain an uncertain transcript with an explicit quality flag than silently "correct" it.

It is preferable to return insufficient evidence than invent an answer.

# 59. ACCEPTANCE CRITERIA FOR MVP

The MVP is successful when:

1. A configured source can be discovered automatically.

2. Candidate enters SQLite queue.

3. Duplicate detection runs.

4. Rights gate runs.

5. Approved source receives a stable Source ID.

6. Original artifact is preserved.

7. SHA-256 is recorded.

8. Processed searchable text is produced.

9. Metadata and provenance are retained.

10. Text is paragraph-aware chunked.

11. Embeddings are generated.

12. Chunks are indexed into Qdrant.

13. Running ingestion again creates no duplicates.

14. Search API retrieves the source.

15. Returned evidence contains Source ID and provenance.

16. Failed processing is visible.

17. Failed processing can resume.
